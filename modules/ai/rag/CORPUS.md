# 广告词库维护指南

`modules/ai/rag/corpus/*.md` 是去广告检索的信号词库（内置层）。这份文档给维护者：怎么加词、怎么审用户提交的 patch、以及哪些词看着该加其实不该加。

用户在扩展设置页补录的词条存在浏览器本地（用户层），**不会自动进这里**；他们通过「导出入库 patch」把词条交过来，由维护者审核后合入。

## 文件格式

一个文件 = 一个品类，文件名即元信息（由 `corpusFileMeta` 解释，不维护额外清单）：

| 文件名 | 信号类别 kind | 默认权重 |
| --- | --- | --- |
| `scripts.md` | script（恰饭话术） | 2 |
| `slang.md` | script（黑话新梗） | 2 |
| `deals.md` | deal（交易信号） | 2 |
| `brands-*.md` | brand（品牌/产品词） | 1 |

行规则：

- 一行一条，`#` 开头是注释，空行忽略；
- `词|N` 覆盖该行的默认权重（1–3 常用：3 = 几乎只在广告里出现，1 = 泛词/弱信号）；
- 词条里不能出现 `|`、换行，也不能以 `#` 开头（会被解析器当权重分隔符或注释）；
- 新建品类就是新建一个 `brands-<品类>.md`，无需改任何代码。

改完之后：

```bash
pnpm test modules/ai/rag/corpus.test.ts   # 语料体检：格式/跨文件去重/迁移回归/哈希敏感
pnpm typecheck && pnpm build
```

## 改动会带来什么

语料内容哈希（FNV-1a）是向量缓存键的一部分。**改任何一个字 → 哈希变 → 所有用户的语料向量缓存失效并在下次识别时重算一次**（一次批量 `/embeddings`，两百条短文本，秒级、几乎不花钱）。所以：

- 加词随时可以加，不需要版本号、不需要通知用户清缓存；
- 但**批量重构（改品类名、调整大量权重）会让所有端点同时重算**，尽量攒成一次提交，别一天推五次；
- 顺序要稳定：词条按文件名排序、文件内按行序，别为了美观重排（重排等于全量失效，且让 diff 不可读）。

## 审核用户 patch 的检查清单

用户导出的 patch 与这里的格式完全同构（按品类分块、`# —— <品类>.md ——` 标题、来源备注写在 `# 来源：` 注释里），可以整块追加进对应文件。追加前后过一遍：

1. **跑体检**：`corpus.test.ts` 的跨文件去重会拦住与内置词重复的提交；哈希敏感测试确认缓存会正常失效。
2. **泛义单字词一律不收**：「美的」「石头」「理想」「小鹏」「网易」「腾讯」这类词在非广告语境里出现频率极高（「美的享受」「这块石头」），进了精确匹配路就是持续误伤。**优先收全称/型号**（石头科技、理想汽车、小米SU7），语义泛化交给向量路兜底。
3. **歧义词降权而不是删除**：确实有广告含义、但同时是高频普通词的，收进来但压到 `|1`，让 LLM 定界层做最终判断。已知的两个例子：
   - `花火|1`：B 站官方商单平台名，同时是《星穹铁道》角色名（游戏视频里必然高频出现）；
   - `联合投稿|1`：B 站合作投稿机制，多数是正常合作而非商单。
4. **权重口径**：`3` 留给「几乎不可能出现在正文里」的强信号（`感谢金主|3`、`本期视频由|3`、`优惠券|3`、`评论区置顶|3`）；`2` 是默认；`1` 是泛词/类目词（`折扣|1`、`大促|1`、`甲方|1`）。用户 patch 里的权重是品类默认值，除非有实证否则不要上调。
5. **品类归组**：品牌词放对应行业文件（放错组不影响召回，但会让品类过滤与后续统计失真）。新行业没有对应文件就新建 `brands-<品类>.md`。
6. **来源注释**：patch 里的 `# 来源：BVxxx 03:20 漏检` 建议保留——它是这个词为什么该收的唯一证据，日后怀疑误伤时可以回去核对。
7. **一次审核的规模**：几十条以内直接合；上百条建议先挑高频的合，其余观察（词库越大，每次哈希变化的重算成本越高，精确匹配遍历也越慢）。

## 什么情况下加词解决不了问题

- **漏检的是一段没有明显关键词的口播**（例如 UP 主只是语气变化）：词表与向量都抓不到，这是 LLM 定界层的活，不要靠堆词硬凑；
- **误检的是正常内容**（比如测评视频反复提品牌名）：加词只会更糟。这类问题要调的是 `MIN_SIMILARITY` 阈值或定界提示词，不是词库；
- **黑话/新梗变体太多**：`slang.md` 只收高频种子词，泛化交给向量路。低价值泛词污染精确路的代价比漏检更高。
